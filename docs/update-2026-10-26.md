# LED, airtime and boot-environment update — 26 October 2026

This record describes one RD15 running as a wired bridge AP. Original logs,
client identifiers, configuration and flash backups remain private. No built
image is distributed.

## Findings that motivated the work

The earlier image had five paired descriptor-allocation/transmission failures
in a short burst, and a later mac80211 warning in the station-statistics
airtime path. The allocation warning comes from an empty preallocated TX
descriptor list, rather than a failed dynamic RAM allocation at that point.
The airtime table switch did not handle RU bandwidth values, and a caller
could use uninitialized overhead after a zero-duration return.

The new hostapd diagnostic measured **ENOENT** for a pairwise key immediately
before an FT association. This supports the pre-association retry hypothesis;
it does not prove uninterrupted traffic after every roam. No common cause
between the TX burst, airtime warning and FT events was established.

## Boot-environment incident and correction

The first interactive update completed and the LED worked, but automatic
boot-success marking failed during a large NAND environment write. Only the
first 4 KiB had been programmed; later padding that had been zero was left
erased. The variables matched the unit's verified backup, but the environment
CRC was invalid.

The device remained powered on during diagnosis. A tightly guarded recovery
preserved every variable and all other bytes, changed the logical CRC to
match the existing padding, and verified the entire partition afterward.
This was specific to that verified state; it is not a generic recovery
recipe or a reason to use another unit's backup.

The final image adds page-sized NAND environment programming with block
readback. After its LuCI update and reboot, the automatic service updated
the slot flag successfully. A fresh independent read confirmed a valid CRC,
slot 0 marked good and failed-boot counters cleared. The previously affected
padding was programmed correctly as well. The exact lower-level cause of
the original large-write failure and long-term NAND behavior remain open.

## Validation

- Two interactive Chrome/LuCI updates completed, with settings retained.
- Kernel and rootfs readback matched the exact input payloads.
- Seven configuration-file hashes and seven protected-partition hashes
  matched the pre-update records, including bootloaders, ART and stock slot.
- Both radios were up; the uplink was 1 Gb/s full duplex. Local DHCP/RA
  services remained stopped for the bridge-AP profile.
- Final AP-to-gateway pings: 20/20, mean 0.488 ms. AP-to-Internet-IP pings:
  5/5, mean 27.084 ms. These are not client navigation tests.
- Available memory was about 37 MiB. The first final-boot log inspection had
  no critical kernel, environment-write, TX allocation or key-install errors.
  This short window does not prove elimination of intermittent events.
- Host C regression checks exercised the actual extracted functions: 19
  airtime cases, five AQL fallback cases and seven NAND-write cases. Controlled
  adapters and synthetic tables isolate contracts; they do not emulate the
  full radio, NAND hardware or power interruption.
- Six existing FDB function contracts and 11 compiled-DTB checks passed.
  Offline image checks and on-device validation without writing also passed.

The owner reports a substantially cooler case than with Xiaomi firmware.
Current internal sensors were around 60 °C. There is no matched stock thermal
or power baseline, so no temperature reduction, power saving or causal
explanation is claimed.
